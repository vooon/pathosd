# Why there is no `exec` check and no embedded scripting

Most health-check daemons grow an escape hatch sooner or later: an `exec` check that runs a shell script, or an embedded language (Lua is the usual one, the way GSLB appliances and some load balancers do it) in which operators write the check logic. pathosd has neither, on purpose, and feature requests for them will be turned into requests for a new typed probe instead. This page records the reasoning so it does not have to be rediscovered.

## What pathosd is

A route originator. Whatever it announces becomes reachable for every client of the routing fabric, and whatever it withdraws disappears from the network. It runs on every node that serves a VIP, usually with capabilities (`CAP_NET_RAW`, `CAP_NET_BIND_SERVICE`) and often as root, and it peers with the routers. Its configuration is reviewed in Git, generated by configuration management and validated against a schema. That configuration is data, not code, and the daemon's attack surface is the set of protocol clients it ships with.

## Why not `exec`

**Configuration becomes code execution.** Anyone who can change the config, or the template that renders it, can run arbitrary commands as the daemon's user on every node. A reviewer can read `type: http` and know what will happen; a reviewer of `command: /usr/local/bin/check.sh` has to read the script, its interpreter, every file it sources and every binary it calls. Configuration management pipelines routinely give more people write access to templates than to shells on the hosts.

**The daemon's guarantees stop at the fork.** pathosd bounds every probe with a deadline, cancels it on shutdown, reports a typed detail and never leaks credentials into logs. A child process inherits none of that: a hung script needs process-group killing, a script that forks leaves orphans, output has to be parsed from text, and secrets end up in environment variables and `/proc/<pid>/cmdline` for every user on the host to read.

**Exit codes carry no information.** A probe returns a status code, rows, a partition count, a certificate expiry; those become `last_detail`, trigger output and metrics, and they are what makes a 3 a.m. withdrawal explainable. An `exec` check returns 0 or 1 and whatever the author remembered to print.

**It is not portable.** pathosd is a static binary that runs on a server, in a scratch container and on an OpenWrt router. Scripts need interpreters, libraries and the same versions of both everywhere; a check that works on the laptop fails on the router.

**It costs more than it looks.** A fork and exec every second on every node is cheap once and expensive at scale; a Python or JVM start per probe is not cheap even once. The protocol probes keep a connection pool or open one socket.

## Why not embedded Lua (or any language)

An embedded interpreter avoids the fork but keeps the rest and adds its own problems:

- It is still code in the config. The review, audit and blast-radius arguments above apply unchanged; the only difference is that the code now runs inside the daemon's address space with its capabilities.
- Sandboxing a language is a permanent liability. Every standard library function that touches files, sockets or the clock has to be removed or wrapped, and every interpreter upgrade can reintroduce one.
- It needs its own bindings for every protocol. The point of a Lua hook is to do things the daemon cannot do, which means exposing sockets, TLS, SASL and parsers to the script, at which point the script is a second, untyped implementation of the probes with none of the validation.
- Timeouts, cancellation and memory limits have to be reimplemented for the VM. A loop in a script is a stuck checker, and a stuck checker on a route originator is either a stale route or a withdrawn fleet.
- Operators have to debug two languages. The typed detail strings and the trigger endpoint exist so that the operator never has to read code to learn why a VIP is down.

## What to do instead

The design bet is that health is a small number of questions with declarative answers:

| Need | Mechanism |
|------|-----------|
| "does the service speak its protocol" | a typed probe: `http`, `dns`, `ping`, `tcp`, `udp`, `grpc`, `listen`, `sql`, `kafka` |
| "is this response what I expect" | a declarative condition on the payload: `response_codes`, `response_regex`, `response_jq` over JSON, `result_jq` over rows, `ok_codes` for gRPC, `topic`/`min_brokers` for Kafka |
| "which combination of signals means healthy" | several checks per VIP with `checks_policy: all | any | <expression>`, compiled and type-checked at load |
| "the operator wants it down" | `lower_priority_file` drains without touching the config; `fail_action` chooses withdraw versus pessimize |
| "never announce what this host does not own" | `require_local_address` |
| "I need to see it now" | the trigger endpoint, `/status` and per-check metrics |

Each condition language is chosen for being total and inspectable: jq cannot open sockets, the policy expressions are boolean algebra over check names and are rejected at validation when a name is misspelled. Neither can hang, allocate without bound or reach outside the data it is given.

When a real signal is missing, the answer is a new probe type in Go, with validation, typed details, metrics, documentation and an e2e scenario, the way `listen`, `sql` and `kafka` were added. That is more work than an `exec` line once, and far less work than operating `exec` lines forever.
